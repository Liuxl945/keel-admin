# 在线开发（低代码平台）能力规划

> 基于当前代码库实际实现编写，不是通用清单。
> 代码基线：`server/src/modules/dev-*`（4 个模块、5443 行）、`admin/src/views/dev/*`（10 个文件）。

---

## 一、现状盘点

### 1.1 已具备的能力

| 能力域 | 已实现 | 落点 |
|---|---|---|
| 数据连接 | MySQL / PostgreSQL，密码 AES 加密，连通性测试，表结构同步入库 | `dev-data-source`、`dev_db_tables` |
| 数据建模 | 7 种列类型（varchar/text/int/decimal/boolean/date/datetime），建表、按字段差异生成 ALTER、表重命名、导入已有表、DDL 预览 | `dev-model.ddl.ts`、`dev-model.publish.ts` |
| 表单设计 | 9 种控件、24 栅格、拖拽、字段与数据库列一一映射、查询字段/列表字段配置 | `dev-form.dto.ts`、`designer.vue` |
| 在线预览 | 真实数据的增删改查（动态 SQL、标识符白名单、参数绑定、优先软删除） | `dev-form.service.ts` 的 `preview*` 系列 |
| 代码生成 | 8 个文件：entity / dto / service / controller / route / api / index.vue / README | `dev-form.codegen.ts`、`dev-model.codegen.ts` |
| 权限与菜单 | 已有 `sys_menus`（DIR/MENU/BUTTON + perm）与 `hasPerm` 中间件 | `menu` 模块、`middlewares/auth.ts` |

### 1.2 关键判断

**当前形态是「设计 → 生成代码 → 人工合并」，不是「设计 → 发布 → 直接可用」。**

证据：

1. `generateDevFormCode()` 只返回 `GeneratedFile[]`（name + content 字符串），前端用 `CodeDialog` 展示，用户手工复制 8 个文件到仓库。
2. 「发布」只改 `dev_forms.status` 和 `version`，不写任何运行时产物、不注册菜单、不建权限点。
3. 唯一能跑起来的链路是 `/dev/form/preview/:id`，但它挂在 `dev:form:list` 权限下，是开发者调试入口，不是业务入口。

**这带来三个直接后果：**

- 业务方无法自助上线，每次都要研发介入合并代码，低代码的价值被吃掉大半。
- 生成代码与 schema 会漂移：改了设计再生成，与已合并的旧代码冲突，只能人工 diff。
- 已生成的页面无法享受平台后续能力升级（排序、导出、审计），每加一个能力都要重新生成一次。

而**好消息**是：`previewDevFormList / previewDevFormCreate / previewDevFormUpdate / previewDevFormDelete` 已经是一套可用的运行时引擎雏形——动态表、动态列、白名单引用、参数绑定、软删除识别都做完了。把它从"预览"提升为"运行时"，是整个规划里性价比最高的一件事。

## 二、核心决策：双轨制

| | 解释执行（运行时） | 代码生成（导出） |
|---|---|---|
| 适用 | 80% 标准业务：列表 + 表单 + CRUD | 20% 需要深度定制：复杂交互、外部集成、特殊算法 |
| 发布方式 | 发布即生效，菜单自动出现 | 导出 ZIP，研发合并进仓库 |
| 升级收益 | 平台能力升级，所有业务页自动受益 | 一次性，后续需重新生成 |
| 定位 | **默认路径** | **逃生舱** |

结论：**运行时是主线，代码生成降级为「导出/二开」**。两者共用同一份 schema 与同一个 DAO，保证行为一致。

## 三、缺口清单

按"阻断上线 → 覆盖真实业务 → 平台化"三档划分，每条都标注工作量（S ≈ 半天内，M ≈ 1-2 天，L ≈ 3 天以上）。

### P0 · 阻断上线（不做就无法交付一个真实业务模块）

| # | 缺口 | 现状问题 | 交付物 | 量 |
|---|---|---|---|---|
| 1 | **运行时引擎** | 只有 dev 预览入口，业务方不可用 | 新模块 `biz-runtime`：`/api/admin/biz/:formKey/rows` 一套 REST + `meta` 接口；统一 `runtime-dao.ts`（从 `preview*` 抽取） | L |
| 2 | **发布即注册菜单与权限** | 发布只改状态，页面无入口 | 发布时事务内创建 `sys_menus`（MENU + 4 个 BUTTON）、绑定 `biz:<formKey>:*` 权限、默认授权超管 | M |
| 3 | **版本快照与回滚** | `version` 字段自增但无内容快照，改了无法回退 | 新表 `dev_form_releases`（schema_json / table_name / published_by / published_at）；发布即快照，支持查看差异与回滚 | M |
| 4 | **关联字段（外键选择器）** | 只能填裸 id，"选部门/选人/选其他表"都做不到 | schema 增 `ref` 配置；运行时远程搜索下拉；列表展示 label 而非 id | L |
| 5 | **列表能力补齐** | 排序写死 `created_at DESC`；只能等值/LIKE；无法导出 | 排序白名单 + 多字段排序；筛选操作符（eq/ne/like/gt/lt/between/in）；CSV/Excel 导出（带行数上限） | M |
| 6 | **业务数据审计** | 改了哪条、谁改的、改前是什么，全无记录 | 新表 `biz_audit_logs`（form_key / row_id / action / before / after / operator / ip）；写操作统一埋点 | M |
| 7 | **工程化底座** | 仍靠 `synchronize: true`，生产不可用 | 引入 migration；新增表全部走 migration；关掉生产同步 | M |

## 四、路线图

### 阶段 0 · 地基（先做，成本低收益高）

- 引入 migration 体系，`dev_*` 四张表与新增表全部纳入
- 抽出 `runtime-dao.ts`：把 `previewBinder / previewQuote / previewWhere` 这些通用件从 `dev-form.service.ts` 提炼为运行时共用层
- 定义 `dev_form_releases` 表结构
- 补 `CLAUDE.md`：在线开发的"发布物"定义、运行时权限命名规范 `biz:<formKey>:<action>`

**验收**：`dev-form.service.ts` 里不再有直接拼 SQL 的业务逻辑，全部走 DAO；生产构建不再依赖 `synchronize`。

### 阶段 1 · 运行时（把"能设计"变成"能用"）

1. `biz-runtime` 模块：meta + rows CRUD + 批量删除
2. 前端通用页 `views/biz/runtime/index.vue`：读 meta → 动态渲染查询区/列表/表单（复用 ProTable、FieldControl）
3. 发布流程改造：写 release 快照 + 建菜单 + 建权限 + 默认授权
4. 审计埋点

**验收**：在后台点「发布」，侧边栏立刻出现「业务应用 → 客户档案」，点进去能对真实表增删改查，无需研发改一行代码。

### 阶段 2 · 业务表达力（把"能用"变成"好用"）

关联字段 → 子表 → 联动规则 → 控件扩充 → 字典接入 → 布局容器 → 列表导出/高级筛选

**验收**：能不开代码，独立做出「订单 + 订单明细 + 客户选择 + 金额合计」这类真实业务模块。

### 阶段 3 · 平台化

应用分组 → 模板市场 → 轻量审批 → 开放 API → 移动端 → 行级权限

## 五、数据模型演进

```
现有
  dev_data_sources      数据连接
  dev_db_tables         表元数据快照
  dev_models            数据模型（建表定义）
  dev_forms             表单设计（schema_json）

新增
  dev_apps              应用分组（表单归属，决定菜单父级）
  dev_form_releases     发布快照（form_id, version, schema_json, table_name, snapshot_time）
  dev_form_relations    关联定义（可选，也可内嵌 schema.ref）
  biz_audit_logs        业务数据变更审计
```

设计取舍：

- **schema 继续存 JSON**，灵活、改动成本低。但把运行时高频读取的部分（列表列、筛选列、权限点）在发布时**冗余到 `dev_form_releases.columns_json`**，避免每次请求解析大 JSON。
- **菜单与权限点不建映射表**，直接在 `sys_menus` 上加 `source_type / source_id` 两列（`source_type='DEV_FORM'`），发布时 upsert，删除表单时级联禁用。这样菜单管理页天然能看到并调整。

## 六、技术决策记录

### D1 · 运行时 SQL 安全边界（最高风险点）

沿用现有三层防护，并补两条：

1. 表名/列名只能来自 `dev_db_tables.columns_json` 白名单（禁止任何用户输入直接进 SQL 标识符位置）
2. 值一律参数绑定（`$1` / `?`）
3. **新增**：排序字段、筛选字段、导出字段全部走同一份白名单校验，不再各写一套
4. **新增**：运行时统一使用只读或受限权限的数据库账号（当前数据连接用的是管理账号，风险过大），至少对运行时链路做语句类型限制（只允许 SELECT/INSERT/UPDATE/DELETE）

### D2 · 代码生成的目标形态

从"展示文本让用户复制"改为**导出 ZIP 下载**。理由：写盘需要服务端对仓库有写权限，生产环境不可行；ZIP 导出既可离线二开，也不污染运行时。

### D3 · 不引入的东西

| 不做 | 原因 |
|---|---|
| 完整 BPMN 流程引擎 | 复杂度远超收益，先用状态机 + 审批节点覆盖 |
| 用户自定义 JS 脚本 | XSS / RCE 风险，沙箱成本高 |
| 可视化大屏 | 与核心链路无关，容易分散资源 |
| 多租户 | 除非明确要对外做 SaaS，否则会污染所有查询 |
